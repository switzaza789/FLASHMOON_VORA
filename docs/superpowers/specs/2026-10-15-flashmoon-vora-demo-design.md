# Flashmoon Vora Demo/Testnet Design

Date: 2026-10-15

## 1. Purpose

สร้างเว็บไซต์เดโมแบบโต้ตอบสำหรับสาธิตแผนการตลาดแบบไบนารีของ Flashmoon Vora (FVR/FM) ให้ผู้ใช้งานทดลองกระบวนการซื้อแพ็กเกจ การจัดวางสมาชิก การคำนวณการจ่ายจำลอง และการติดตามเส้นทางเงินได้ โดยไม่รับเงินจริง ไม่เชื่อมต่อบล็อกเชน และไม่ใช้กระเป๋าเงินจริง

ทุกหน้าต้องแสดงข้อความว่า `Demo/Testnet — ไม่ใช่การลงทุนจริงและไม่มีการโอนเงินจริง` หรือคำแปลภาษาอังกฤษที่เทียบเท่า

## 2. Scope ที่ยืนยันแล้ว

- รองรับภาษาไทยและภาษาอังกฤษ พร้อมตัวสลับภาษา
- เริ่มจากระบบว่าง ผู้ใช้สร้างสมาชิกและสายงานเอง
- มีบัญชี Demo User และ Demo Admin พร้อมการสมัครบัญชีใหม่
- ผู้ใช้กดซื้อแพ็กเกจจำลอง 100 USDT ได้โดยไม่ต้องเติมยอด
- รองรับการวางสมาชิกเองทางซ้าย/ขวา และการวางอัตโนมัติ
- แสดง Binary Tree แบบขยาย/ย่อและอ่านง่าย
- แสดงประวัติธุรกรรมและเส้นทางเงินแบบ `ต้นทาง → กติกา → ผู้รับ → กระเป๋า`
- แสดงรายได้แยกตาม User และประเภท: ค่าแนะนำ, Uni, โครงสร้าง และ FVR/FM
- มีการคำนวณทันทีเมื่อเกิดการซื้อ และมีรอบประมวลผลที่ Admin สั่งได้
- มีหน้า Admin สำหรับดูสมาชิก ผังรวม ธุรกรรม และการจ่ายเงินจำลอง

## 3. กติกาการจ่ายที่ใช้ในเดโมระยะแรก

ธุรกรรมซื้อหนึ่งครั้งมีมูลค่า 100 USDT จำลอง และแสดงการจัดสรรตามข้อมูลที่ให้มา:

- ค่าแนะนำ 30%
- Uni ตามสายเลือด 10 ชั้น รวม 10% (เบื้องต้นตีความเป็นชั้นละ 1%)
- โครงสร้าง 5 ชั้น รวม 50% (เบื้องต้นตีความเป็นชั้นละ 10%)
- FVR/FM 10% สำหรับกิจกรรมวงล้อ

กติกา “กัน 40% จากรายได้โครงสร้างของทุก ID เพื่อสะสมครบ 100 USDT แล้วเกิดใหม่” ยังไม่สรุป จึงต้องแยกเป็นกติกาที่ตั้งค่าได้และปิดใช้งานไว้ก่อน ห้ามฝังสูตรถาวรในระบบจนกว่าจะยืนยันรายละเอียด

## 4. ประสบการณ์และหน้าจอ

### Landing / Entry

อธิบายว่าเป็นเดโมแบบจำลอง พร้อมปุ่มสลับภาษา สมัครสมาชิก และเข้าสู่ Demo User/Admin

### User Dashboard

แสดงยอดจำลอง สรุปรายได้ตามประเภท จำนวนสมาชิกที่แนะนำ สถานะการซื้อ และทางลัดไปยัง Binary Tree, ธุรกรรม และรายละเอียดรายได้

### Purchase Flow

ปุ่มซื้อแพ็กเกจ 100 USDT จำลอง แสดงหน้าสรุปก่อนยืนยัน แล้วสร้างธุรกรรมและผลการจัดสรรให้ดูทันที โดยไม่หักเงินจากยอดเงินจริง

### Binary Tree

ใช้แผนผังที่อ่านง่าย รองรับการขยาย/ย่อ เลือกสมาชิกเพื่อดูรายละเอียด และแสดงฝั่งซ้าย/ขวา ชั้น ตำแหน่ง ยอดซื้อ และรายได้

ตัวอย่างโครงสร้าง:

```text
ผู้แนะนำหลัก
├── ฝั่งซ้าย
│   ├── สมาชิก A
│   │   ├── สมาชิก C
│   │   └── สมาชิก D
│   └── สมาชิก B
└── ฝั่งขวา
    ├── สมาชิก E
    └── สมาชิก F
```

### Money Flow / Transaction Explorer

แสดงภาพรวมและรายละเอียดแบบเจาะรายการ:

```text
User ต้นทาง
    │ ซื้อแพ็กเกจ 100 USDT
    ▼
ระบบคำนวณการแบ่ง
    ├── ค่าแนะนำ → User ผู้แนะนำ
    ├── Uni 10 ชั้น → User ตามสายเลือด
    ├── โครงสร้าง 5 ชั้น → User ใน Binary Tree
    └── FVR/FM 10% → กระเป๋า FVR/FM
```

ทุกแถวต้องระบุผู้ส่ง ผู้รับ กติกาที่ใช้ จำนวน สถานะ และเวลา และสามารถเปิดดูเส้นทางเงินของธุรกรรมเดียวได้

### Earnings

ตารางและการ์ดสรุปรายได้ของแต่ละ User แยกตามค่าแนะนำ, Uni, โครงสร้าง, FVR/FM พร้อมยอดรวมและประวัติรายการ

### Admin Dashboard

ดูสมาชิกทั้งหมด ผังรวม สถานะธุรกรรม สรุปการจ่าย และสั่ง “ประมวลผลรอบจ่าย” ได้ การประมวลผลต้องแสดงผลลัพธ์และรายการที่ได้รับผลกระทบอย่างชัดเจน

## 5. โครงสร้างข้อมูลเชิงแนวคิด

- `users`: บัญชี ผู้แนะนำ บทบาท ภาษา และสถานะ
- `binary_positions`: parent, side, depth และตำแหน่งในต้นไม้
- `purchases`: ผู้ซื้อ มูลค่าจำลอง เวลา และสถานะ
- `payouts`: purchase, source user, recipient user, rule type, amount, wallet label, status
- `processing_runs`: รอบประมวลผล เวลา ผู้สั่ง และผลลัพธ์
- `settings`: อัตราการจ่ายและสถานะกติกาการสะสม/เกิดใหม่

ข้อมูลเดโมสามารถเริ่มจาก local persistence ได้ และต้องมีทางรีเซ็ตกลับเป็นระบบว่างโดยไม่ลบโค้ดหรือข้อมูลผู้ใช้จริง เพราะระบบนี้ไม่มีข้อมูลเงินจริง

## 6. หลักการทำงานและข้อผิดพลาด

- ถ้าไม่มีผู้รับตามชั้นที่กำหนด ให้บันทึกผลเป็น `unmatched` และแสดงเหตุผล ไม่จ่ายให้ผู้ใช้ที่ไม่เกี่ยวข้องโดยอัตโนมัติ
- ป้องกันการซื้อซ้ำจากการกดปุ่มซ้ำด้วย transaction id และสถานะที่ชัดเจน
- หากผังไม่สามารถวางตำแหน่งได้ ต้องแจ้งตำแหน่งที่ว่างหรือเหตุผลที่วางไม่ได้
- Admin actions ต้องแสดงคำยืนยันก่อนประมวลผล และเก็บประวัติผู้สั่ง
- แยกข้อมูลจำลองออกจากเงินจริงโดยใช้ป้าย Demo/Testnet และชื่อกระเป๋าเชิงสัญลักษณ์เท่านั้น

## 7. การตรวจสอบ

- ทดสอบสมัครและเข้าสู่ระบบทั้ง User/Admin
- ทดสอบวางสมาชิกเองซ้าย/ขวาและวางอัตโนมัติ
- ทดสอบซื้อแพ็กเกจและตรวจสอบยอดรวมการจัดสรร 100%
- ทดสอบดูเส้นทางเงินจาก User ต้นทางไปยังผู้รับแต่ละราย
- ทดสอบกรณีสายเลือดหรือโครงสร้างไม่ครบชั้น
- ทดสอบรอบประมวลผลและป้องกันการจ่ายซ้ำ
- ทดสอบตัวสลับภาษาและ responsive layout
- ตรวจสอบว่าไม่มีการเรียก payment gateway, wallet connection หรือ blockchain จริง

## 8. สิ่งที่ยังต้องยืนยันภายหลัง

1. สูตรที่แน่นอนของเงินสะสม 40% ต่อ ID
2. เงื่อนไขและตำแหน่งของการเกิดใหม่เมื่อครบ 100 USDT
3. รายละเอียดกิจกรรมวงล้อ FVR/FM เช่น ใครมีสิทธิ์หมุนและใช้ยอดใดเป็นเกณฑ์
